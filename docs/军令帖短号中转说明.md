# 军令帖短号中转说明（后台开发用 · 白话 · 不进游戏）

> 本文是 `src/ticket-store.js` / `bridge.html` / `supabase/schema.sql` / `miniprogram/utils/relay.js` 的后台全本。
> **游戏内一个字都不出现**；游戏里仍是「系统 → 导出军令帖」那一段 base64url 口令，格式一行没改。
> 资料总目见 `docs/建安五年官渡舆图史料汇总.md` §16，权属与证据链见 `docs/创作决策日志.md`。

## 一、是什么，不是什么

| 是 | 不是 |
| --- | --- |
| 把几千字符的整帖换成六位短号，短号走会话 / 分享卡片 / 手抄 | 加密、鉴权、账号体系 |
| 一张只存「字符串 + 取件码 + 过期时间」的表，加 RLS 策略 | 服务器权威状态机、匹配、防作弊、常驻房间 |
| 网页版旁边一个独立「传帖台」页面，不加载游戏逻辑 | 游戏客户端、Web 主包的第二个入口 |
| 对 `src/sync.js` 命令日志 / 状态指纹 / 确定性重放的**零改动** | 把策略层搬上云端 |

一句话：**它只解决「长口令不好传」，不解决「谁裁定这一旬」。** 权威状态机仍在本地，两端各自重放，指纹仍由 `src/sync.js` 比对。

## 二、链路

```
网页版 一旬推进 → 系统页「导出军令帖」
      → encodeTicket({ v, game, version, date, hash, save, logTail })   [src/sync.js，未改]
      ↓ 粘进独立页 bridge.html（传帖台）
putTicket(store, 整帖)
      → describeTicket 校字段 / 长度 / 字符集 / game / save.v
      → makeShortId 六位短号（去掉 0/1/I/O）
      → POST /rest/v1/tickets  { id, payload, hash, version, map_id, turn, expires_at }
      ↓ 短号（如 K7M2QP）
微信会话 / 分享卡片 ?sid=K7M2QP / 口头念 / 手抄
      ↓ 对方
bridge.html 填短号 → takeTicket(store, id, {burn})
      → GET /rest/v1/tickets?id=eq.K7M2QP&select=...
      → describeTicket 再校一遍（防库里被塞垃圾）
      → 复制整帖 → 粘回网页版「导入」→ loadGame() → 接续一旬
```

`store` 是 `put / get / del` 三方法接口：`createMemoryStore()` 供单测与离线回退，`createRestStore()` 是通用 PostgREST 形状，`createSupabaseStore()` 只是把项目地址与 anon key 转成 endpoint + headers。**将来换自有域名反代或微信云函数中转，只换 endpoint 与 headers，上层两个函数一行不动。**

## 三、表结构与 RLS（`supabase/schema.sql`）

| 字段 | 类型 | 约束 | 用途 |
| --- | --- | --- | --- |
| `id` | text PK | 6 位、字符集 `2-9A-HJ-NP-Z` | 短号，32^6 ≈ 10.7 亿空间 |
| `payload` | text | 1–20000 字符 | 整段 base64url 军令帖，明文 |
| `hash` / `version` / `map_id` / `turn` | — | 默认空 / 0 | 取帖时展示用，不参与判定 |
| `created_at` / `expires_at` | timestamptz | 默认 now() / now()+7d | 读侧过滤过期 |

三条 RLS 策略：

- **insert（anon）**：`with check` 限制 id 长度与字符集、payload ≤ 20000、`expires_at > now()` 且 `≤ now()+7 days`。最后一条很关键——否则客户端可以把 TTL 写成一百年，表永远不清。
- **select（anon）**：`using (expires_at > now())`。过期行读不到，但**不会自动消失**，需要定期手工 `delete from public.tickets where expires_at <= now();`（不必上 pg_cron）。
- **delete（anon）**：`using (expires_at > now())`，供「取后即焚」。

**刻意不给 `update`**：短号一旦发出，帖不可被改写，否则对方取到的可能不是你发的那一旬。`grant select, insert, delete on public.tickets to anon` 明确排除 update。

主键冲突（409 / 23505）由 `putTicket` 换号重试处理，**绝不覆盖已有帖**，单测有断言。

## 四、anon key 不是秘密，service_role key 是

这是上一轮 PAT 那段话的同一条原则，落成了代码护栏：

- Supabase 的 **anon public key 按设计可公开**，配合 RLS 才成立安全边界；前端必须带它，硬编码进页面不算泄露。
- **service_role key 绕过 RLS**，一旦进页面即等同泄露；`authenticated` JWT 属于某个登录用户，同样不该写死在静态页。
- `assertPublicKey()` 三道拦截：字面含 `service_role` 拒收；解 JWT payload 得 `role === 'service_role'` 拒收；`role` 为其它非 anon 值拒收。自托管非 JWT 的普通字符串放行。
- key 只放在 `apikey` / `Authorization` 头里，**不进 URL query**，单测断言过。
- `bridge.html` 把配置存在浏览器 `localStorage`，不写进仓库、不随页面发出；仓库里只有 placeholder，没有任何真实项目地址或 key。

## 五、成本（按刊例价算，不打包票）

免费层额度 [citation:7]：出流量 5 GB、数据库每项目 500 MB、50,000 MAU、Edge Functions 50 万次调用、实时消息 200 万、实时峰值连接 200、存储 1 GB；每个组织最多 2 个活跃免费项目，且**免费项目在低活动一周后会暂停**，Pro 起价 $25/月（含 8 GB 磁盘、250 GB 出流量、不暂停）[citation:8]。

本链路不用 Auth、不用 Realtime、不用 Edge Functions，只碰 REST 与数据库：

| 项 | 估算 | 说明 |
| --- | --- | --- |
| 单次发帖 | POST 请求体 ≤ 20 KB，响应体近 0 | 入流量不计出流量 |
| 单次取帖 | GET 响应 ≤ 20 KB | 出流量主要来自这里 |
| 5 GB 出流量 ≈ | **约 25 万次取帖 / 月** | 5×1024×1024 KB ÷ 20 KB |
| 500 MB 数据库 ≈ | **约 2.5 万行同时在七日窗口内** | 每行按 20 KB 上限算 |
| 月费 | **0 元**（免费层内） | 超出按量：Pro 每 GB 出流量 $0.09、每 GB 磁盘 $0.125 [citation:7] |

对比之前算过的微信云开发：异步军令帖约 4 元/月、常驻 WebSocket 实时房间约 600 元/月/百房。**Supabase 免费层在算力上更便宜，但它引入了一个微信私有链路没有的东西：外部域名**（见下一节）。

两个必须写清的非钱成本：

1. **免费项目会暂停**。军令帖是按旬异步传，一局可能隔几天才动一次，正好撞上「一周低活动暂停」。恢复要在控制台手动点，不像 GitHub Pages 那样永远在线。真要长期无人值守，得 Pro 或加定时探活。
2. **匿名可写 = 任何人都能灌水**。免费层不自带速率限制，`with check` 只挡格式不挡频率。要收紧，得在 Edge Function 或自建网关做 IP / 短号配额，那一步会重新引入计费与部署。

## 六、小程序为什么还是不联网（最重要的一节）

`wx.request` 访问外部后端，要求 HTTPS + **已 ICP 备案域名**，且要配进小程序后台的 request 合法域名、通过域名归属校验 。第三方项目的 `*.supabase.co` 域名不归本主体所有，没法备案、也没法放校验文件。这与「个人主体行不行」无关——企业主体同样卡在域名归属上。

所以三条路摆清：

| 路 | 做法 | 代价 |
| --- | --- | --- |
| **A（当前）** | 小程序只传短号 / 整帖，不联网；兑换在 Web 传帖台 | 零合规增量，多一次「切到网页」 |
| **B** | 自有已备案域名反代 Supabase REST，`createRestStore({endpoint:'https://自有域名/...'})` | 要买域名、备案、配反代与证书；上层代码零改动 |
| **C** | 微信云开发中转：云函数走 `callContainer` 私有链路，再把请求转给 Supabase | 免域名，但回到云开发计费；等于把两套后台叠起来 |

当前选 A。小程序侧因此只多了 `utils/relay.js`（短号格式校验 + 一句提示）、一个短号输入框、以及分享卡片 `?sid=K7M2QP`——**六位短号足够短，进 path 不会被截断**，但点开卡片只是「看见短号」，不能「直接接一局」。这句话在 README 里如实写着，没有包装成一键接续。

## 七、安全边界与取舍

- **短号是取件码，不是密码**。拿到即可读帖，靠 32^6 的不可枚举性，不靠保密性。别把短号贴到公开论坛，也别往帖里放凭证、手机号、真实姓名——`payload` 是明文。
- **库里不做重放**，所以表里被塞垃圾也不会影响任何人的局面：`takeTicket` 出场再 `describeTicket` 校一遍，坏帖直接抛错。
- **不解决防作弊**。play-by-email 本来就是「双方各自重放、比对指纹」，谁改了本地存档，对方一对指纹就知道。这套机制仍在 `src/sync.js`，中转层没动它。
- **不做实时同步**。仍是按旬异步，没有常驻连接、没有帧广播、没有服务器裁定。之前算过的实时成本与「为空气付钱」结论不变。

## 十二、服务端函数直连（项目口令形态，前端零 key）

用户已建好后端项目，给到的是**项目 id + 项目口令 + 服务器自动**，不是 anon key。
这时不该再去找 anon / publishable key：项目口令能直连数据库，正解是让服务端持有它，
前端只打一个函数地址。本节只写形状，真实 id、口令、地址一律不进仓库。

| | 表直连（§十一） | 服务端函数（本节） |
| --- | --- | --- |
| 前端要填 | Project URL + anon public key | **只有一个函数地址** |
| 谁持有秘密 | 无（anon 本就可公开，靠 RLS） | 服务端环境变量 `DATABASE_URL` / service role |
| 项目口令去向 | 不用 | **只进环境变量 / SQL Editor，绝不进页面、不进仓库** |
| 需要控制台再取东西 | 要（Settings → API） | **不用**，给的已经够了 |
| 本环境能否跑通 | 不能（域名可达但出口 403） | 不能（5432/6543 不可达、函数未部署） |

**函数约定**：单个 `POST` endpoint，body `{ op: 'put'|'get'|'del', id?, rec? }`，
返回 `{ ok, conflict?, row? }`。字段与 `createRestStore` 完全一致，所以上层
`putTicket / takeTicket`、短号去重、七日过期、取后即焚一行没改。
前端实现是 `src/ticket-store.js` 的 `createFunctionStore()`，请求头**故意不带**
`apikey` / `Authorization`——这是「零 key」的硬证据，单测与烟测都断言了它。

**服务端最小骨架**（`Deno.serve`，口令从环境变量读，不落文件）：

```js
// supabase/functions/relay/index.ts（示意，本环境未部署、未执行）
const url = Deno.env.get('DATABASE_URL');   // 由项目口令拼成，只在控制台 Secrets 里设
Deno.serve(async (req) => {
  const { op, id, rec } = await req.json();
  // 用 postgres 客户端连库，执行与 schema.sql 同构的 upsert / select / delete；
  // 连接串与任何 key 都不出现在响应里。
  return Response.json({ ok: true, row: null });
});
```

`DATABASE_URL` 形状：`postgresql://postgres:<项目口令>@db.<project-ref>.supabase.co:5432/postgres`
（池化端口 6543 按项目实际区域选）。**`<项目口令>` 是占位符**，真值不写进本文件。

**落地三步（不需要改任何前端代码）**：
1. SQL Editor 跑一次 `supabase/schema.sql` 建表；
2. 把函数部署到 `https://<project-ref>.supabase.co/functions/v1/relay`，在项目 Secrets 里设 `DATABASE_URL`；
3. 传帖台切「服务端函数（免 key）」，填这一个地址 →「记于本机」，或用 `#m=fn&e=<地址>` 装配链接。

**如实边界**：本轮探测到项目域名有 CDN 解析记录，但沙盒出口对 `.supabase.co` 一律
`403 policy_default_denied`，`db.` 子域不解析、5432/6543 不可达，所以**建表、部署、
RLS/CORS、真实收发都没在本环境执行过**。链路与护栏已备好，接上真实函数即可用；
上面三步里前两步必须在项目控制台完成，不能由静态页代劳。


## 十三、Agent Secret 接入（本轮）

用户已在仓库 `Settings → Secrets → Agents` 把项目口令存为 **`sup`**。
这条正好补上 §十二 里「服务端持有秘密」的载体，但有三点不能含糊：

1. **我这个会话读不到它的明文**。GitHub 的 secret 只在 Actions / agent 运行时注入，
   REST API 只返回名字、永不返回值；那个 settings 页需登录，解析也失败。
   值在对话里出现过，所以我知道它是什么，但**不会去 API 读、不会写进任何文件**。
2. **消费它的地方是 `.github/workflows/relay-schema.yml`**：`workflow_dispatch` 手动触发，
   用 `PGPASSWORD: ${{ secrets.sup }}` 在 GitHub 侧网络跑 `supabase/schema.sql`。
   主机 / 端口 / 用户 / 库名走仓库 Variables（非秘密，按控制台填），不写死。
   这解决的是「本沙盒到 `.supabase.co` 一律 403、5432/6543 不可达」——**换 GitHub 的网络去连**。
3. **只自动化了建表，不是全链路**。Edge Function 部署还需要 `SUPABASE_ACCESS_TOKEN`；
   前端「表直连」也仍要 anon key。所以现在能点一下自动跑的是「表建好」，
   不是「传帖台立刻能收发」。函数没部署时页面会如实报错，不静默吞。

零明文护栏同步加在 `scripts/check-map.mjs`：项目 id、项目口令、便签地址
一律不许出现在被跟踪文件里；workflow 里只有 `${{ secrets.sup }}` 这个引用名。


## 十四、Agent Secret 口径修正与可部署函数骨架（本轮）

### 14.1 「登不进 sup」到底卡在哪

用户说没法登录 Supabase 控制台、只在仓库 `Settings → Secrets → Agents` 存了 `sup`。
本轮用 API 核过状态：**Actions secrets 0 个、Variables 0 个、relay-schema 无运行记录**。

于是 §十三 那句「消费它的地方是 `.github/workflows/relay-schema.yml`」**不成立**：
`Secrets → Agents` 与 `Secrets and variables → Actions` 是两个命名空间，
workflow 里的 `${{ secrets.sup }}` 只读后者。Agent namespace 没有公开的 REST 列表接口
（`/actions/agent-secrets`、`/secrets/agents` 均 404），本会话也读不到它的明文。

**所以不需要「登录」**：要么在 Actions 里另建同名 secret（一次性、控制台点几下），
要么改走 14.2 的函数骨架（完全绕开 psql 直连）。本轮**没有**替用户创建任何 secret、
没有触发过 workflow、Variables 仍为空——上一轮那次尝试被中断，仓库里什么都没留下。

### 14.2 `supabase/functions/relay/index.ts` 已落地

上一轮 §十二 只有一段示意，这轮补成**可部署文件**：Deno.serve + `npm:pg` 连接池，
契约与 `createFunctionStore()` 逐字对齐（`op` 白名单 / `{ok, conflict?, row?}`）。

- 连接串只从 `SUPABASE_DB_URL`（Edge 运行时内置）或 `DATABASE_URL`（项目 Secrets）读；
- 请求头零 key，函数自己就是唯一入口；
- `expires_at` 由服务端重算，不信客户端，与 `schema.sql` 的 RLS `with check` 同口径；
- 全部 SQL 参数化；错误只回泛化文案，细节进服务端日志，不漏库结构；
- CORS 只放 `content-type` 与 `POST/OPTIONS`；仍无速率限制、无审计、过期行不自动清理。

**部署形状**（真实 ref / token 都不写进仓库）：

```
supabase login                       # 或 SUPABASE_ACCESS_TOKEN 由 CI 环境注入
supabase functions deploy relay --project-ref <ref>
```

传帖台切「服务端函数（免 key）」，填 `https://<ref>.supabase.co/functions/v1/relay`
即可，前端不需要 anon key，也不需要 `sup` 出现在任何页面。
**函数未部署 / 未在本环境执行过**：沙盒对 `.supabase.co` 出口 403、
5432/6543 不可达，真实收发、RLS、CORS 都仍未验。
